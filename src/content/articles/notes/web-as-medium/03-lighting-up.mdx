这条笔记记录第一批机制从方案到全绿的过程。它本身也是个实验：
**建造这个媒介引擎的过程，就用这个媒介引擎来记录。**

## 施工怎么排

十个任务按文件相交性排成两个波次：内容模型、规则引擎、源码插件先行；
组件与页面布局随后。真正的约束不是逻辑依赖，而是**哪些任务会碰同一个文件**——
`lab.astro`、`global.css`、组件 README 是三个人人都想写两行的地方，
碰同一文件的任务只能串行。这大概是多代理协作最不浪漫但最真实的一课。

## 翻车记录

- **两个子任务死于会话额度**。SideNote 和 poster 档的执行代理跑到一半被限流掐断，
  最后由主会话直接补写。教训：并行度不是免费的，要给"谁都可能死在半路"留预案。
- **规则引擎的注册表接口长歪了一点**。设计稿里触发器签名是三个参数，
  实现时发现注册表是模块级常量、拿不到每个引擎实例的上下文，只好加了第四个参数
  `env: { root, reducedMotion }`。方案是纸上的，模块作用域是真实的。
- **块级目标的变色效果一度看不见**——外层 div 被不透明的内层盖住了。
  修法是给 `div.rg-tint-* > *` 也着色。"页面即房间"的比喻很美，
  但房间里的物件有层叠上下文。

## 全绿那一刻测的是什么

Playwright 测的不是源码，是 `dist/` 构建产物——静态托管伺服出来的真实页面：
规则被点击后计数属性真的变成 1；取消勾选后效果类真的被摘掉；
禁 JS 时规则清单真的降级成一段通顺散文；reduced-motion 下位移动画真的没跑。
**每一条契约都对应一条会失败的断言**，这是"内容永不被劫持"从原则变成机制的方式。

## 留给下一条笔记的问题

规则引擎目前只有五种谓词、五种效果，全部是注册表里的一项。
下一个值得试的谓词是"当读者读到第 N 段时"——它比滚动深度更接近"阅读"本身。
但在加任何一项之前，先回答那个老问题：**它给叙事增加了什么档位？**
